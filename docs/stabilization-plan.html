02

Critical — fix before anything else

Both are verified in source. Together they explain the two most-felt symptoms: "voice randomly disconnects" and "the server hangs when we delete things."

Criticalrace · resource leakverified in source CRIT-1

Voice/DM cleanup is keyed by userId with no socket-ownership check — the client's own reconnect flow kills its session

Where: voiceHandler.ts:899 leaveCurrentVoiceChannel tears down channelUsers.get(userId) using socket.data.voiceChannelId, never comparing the departing socket to the session owner. Same shape in dmVoiceHandler.ts:127.

Failure: a network blip makes Socket.IO reconnect with a new socket; the client auto re-emits voice:join, which overwrites the per-user media entry (voiceHandler.ts:244). When the old socket's ping finally times out (~10–35s later), its disconnecting handler finds the new session under that userId and closes its transports/producers — kicking the user out of voice and leaking two UDP ports each time. For DM calls it force-ends the call and re-rings the peer.

Fix  Store socketId on the media/call state; both leave paths must no-op unless state.socketId === socket.id. Add regression tests for reconnect-rejoin and stale-socket-disconnect.
Criticalschema · performanceverified in source CRIT-2

Missing indexes turn routine deletes into full-table scans and every socket connect into a sequential scan

Where: schema.prisma — no index on messages.reply_to_id, messages.author_id, a plain messages.created_at, server_members.server_id (PK is [userId, serverId]), or conversations.user2_id.

Failure: reply_to_id's ON DELETE SET NULL runs UPDATE … WHERE reply_to_id=$1 per deleted row; with no index, deleting a channel of 50k messages scans the messages table 50k times (O(N²) — can lock the DB for minutes to hours). conversations.user2_id is scanned twice on every socket connect; messages.created_at is full-scanned every 5 seconds by the admin live-metrics emitter.

Fix  One additive migration (indexes only, no data change) covering the five above plus the low-severity cascade indexes in §5. Zero application-code risk.

04

Screen share — root cause

The TODO marked this "fixed," but it regressed because the fix was verified only on the first share of a session — which always works. The failure is deterministic on the second share. Three independent faults compound.

1

Producer slot leak → second share hangs the client (the core bug)

There is no voice:producer:close event anywhere in the protocol (confirmed in types.ts). Stopping a share closes producers client-side only; the server keeps them until the user leaves the channel. Mic (1) + screen video (2) + screen audio (3) → stop → share again: video is producer 4, and screen audio hits the producers.size >= 4 cap (voiceHandler.ts:410). The cap path returns without calling the ACK callback, and the client's produce() awaits that ACK with no timeout — so it hangs forever, wedging the whole send transport. Viewers see nothing; the OS capture indicator stays on.

2

Screen system-audio is muted for any muted or push-to-talk sharer

Every mute path — produce-time pause, pauseUserAudio, voice:mute/deaf/server_mute, and all client toggles + the PTT hook — pauses every audio-kind producer with no appData.type filter. PTT users are permanently server-muted, so their stream carries game audio only while holding the key. "Screen share has no sound."

3

Video is starved to blur

A hard 1.5 Mbps cap on every recv transport (shared across all consumers), a 600 kbps bandwidth seed, and a video producer created with no encodings/maxBitrate, no contentHint, and VP8-only. 1080p+ desktop content is permanently unreadable, with a multi-second blurry warm-up per viewer.

Adjacent defects that must be handled in the same change: the screen-audio consumer arrives as kind:'audio' and is misrouted as mic audio on viewers (survives deafen; orphans the mic <audio> element); stale isScreenSharing after transport auto-rejoin; capture stream + half-created producer leaked on the error path with no user feedback; and — critically — once #1 is fixed by closing screen producers on stop, voiceStore.ts:976 will start deleting the sharer's mic element on every stop unless fixed together.

Fix shape: add a voice:producer:close event (client → server, closes the specific producer + notifies consumers); ACK every voice:produce failure path and add a client-side timeout; filter all pause/resume by appData.type so screen audio is never silence/mute-paused; route the screen-audio consumer by appData, not kind; and give the video producer real encodings + contentHint:'detail' and lift the recv cap for screen video. This is a coordinated server+client change with its own test pass (share → stop → share×3, muted sharer, PTT sharer, deafened viewer, late joiner).

Encryption — securing user data

"Encryption" splits into two very different layers. The roadmap and Architecture.md already commit to the honest framing: server channels stay protected by the server (TLS + at-rest), DMs get optional protection from the server (E2E). I'd build it in that order.

A ✓ SHIPPEDBaseline data-at-rest & in-transit — no UX changecode shipped 2026-07-06 · infra steps in DEPLOYMENT.md §12/§15/§19

Verifiable "the data is secured" without touching the product surface. Mostly infra + a few code checks.

  • ✅ HSTS: 1-year + includeSubDomains from helmet in production; nginx add_header for static files documented (DEPLOYMENT.md §12) in transit
  • ✅ Backups: pg_dump now GPG-encrypted (AES-256 symmetric) in the deploy guide; encrypted data volume documented as optional for new instances (§19) disk-level
  • ✅ S3 SSE: S3_SSE=AES256 env flag applies ServerSideEncryption to every presigned PUT (presigner hoists it to the query string — zero client changes) attachments/avatars
  • ✅ Logging audit (agent-swept all 3 apps): no tokens/passwords/secrets logged anywhere; fixed the 3 residual gaps — nodemailer error objects (could carry recipient email) now log message-only, invite codes redacted from JSON access logs, TOTP plaintext fallback now FAILS CLOSED in production (boot refuses + encryptSecret throws)
  • ✅ Secret columns audit: password bcrypt-12, backup codes bcrypt-10, reset/verification tokens SHA-256, TOTP secrets AES-256-GCM, refresh/trusted-device tokens stateless (never stored). Only borderline: Invite.code plaintext — accepted (single-use, deletable, now log-redacted)
  • ⏭️ App-layer encryption of DM/message content: skipped deliberately — it would break the pg_trgm server-search index shipped in P3 (MED-14), and phase B's E2E supersedes it for DMs optional
BEnd-to-end encrypted DMs — MVP (opt-in, text)

The privacy differentiator. Server stores ciphertext + public keys only; it cannot read message bodies.

  • New UserDevice model: identity public key (X25519), signed prekey, one-time prekeys, registrationId — private keys never leave the device (Tauri secure storage / OS keychain)
  • Adopt a vetted library (Signal Protocol / Double Ratchet, e.g. libsignal) rather than hand-rolling crypto — client-side only, no third-party service, consistent with the privacy stance
  • Server endpoints serve prekey bundles; message ciphertext stored as an opaque blob with only sender/recipient/timestamp metadata
  • Opt-in per conversation with a key-verification step (safety numbers / QR); "E2E Encrypted" badge
  • Graceful degradation: recipient without keys (old client) → fall back with an explicit warning, never silently plaintext
  • Single device first; multi-device fanout in Phase C
CE2E completeness

Everything a DM can contain, plus multi-device.

  • Client-side encrypted attachments: AES-256-GCM before S3 upload, file key wrapped in the E2E message; proxy/cleanup work unchanged on ciphertext
  • Multi-device: per-recipient-device session fanout; encrypted key backup so a new device can be provisioned
  • Client-side search over the locally-decrypted cache (server search can't see ciphertext)

The honest trade-offs — E2E is not free, and each of these is a product decision, not just an engineering one:

Server-side search
Breaks for E2E conversations — the server can't index ciphertext. Either exclude E2E DMs from server search or move to client-side search over the local cache.
Notifications
Push/desktop can't show message content server-side — only "New message"; the body is resolved on-device after decrypt.
Moderation / reports
You can't server-inspect E2E DM content (this aligns with the privacy stance). Reporting an E2E DM must attach client-side plaintext chosen by the reporter.
History & device loss
A new device can't read old messages without encrypted key backup; losing all keys means losing message history — by design.
Scope
DMs only. Server channels (many recipients, moderation, search) stay server-side encrypted — E2E group channels are a much larger, separate effort.
